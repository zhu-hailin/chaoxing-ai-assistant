# UEditor 双命名模式预填

日期：2026-10-22。基于本地最新源码，版本保持 1.28.1。

## 原因

`readQuestionUEditor()` 原先仅查询 `textarea[id^="answerEditor"]` 并要求 `answerEditor` 加数字。用户提供的新现场采用 `answer215132900` 至 `answer215132906`，因此未进入 UEditor 绑定，`capabilities.prefill`、`binding.canPrefill` 和题目图可写关系均未放行，预填候选为空。

既有题目适配器优先使用外层 `.singleQuesId`；本次保留题目 ID 生成逻辑，内部 `.TiMu[data="4"]` 不参与新模式身份验证。

## 修改

- `sources/question-parser.js`：支持两种命名模式，分步返回具体失败诊断，补充文本响应控件无法唯一对应的诊断。
- `implementation.js`：生成答案后显示明确的 UEditor 关联错误，并保留独立的人工操作或答案策略限制。沿用原有按钮状态计算。
- `CHANGELOG.md`、本记录及生成的完整用户脚本。

修改前备份：`work/ueditor-answer-id-20261022/before/`。

## 识别与保护

旧模式 `answerEditor{数字}` 继续通过现有实例的精确 key 建立映射，数字后缀不强制等于题目 ID，字段 name 沿用原有唯一性要求。

新模式 `answer{ID}` 只有存在 key 对应的实例或当前题目内的原生 UEditor 容器及 iframe 证据时，才进入 UEditor 校验。没有这些证据的普通 textarea 继续使用普通文本框路径，隐藏 input 不参与编辑器识别。

新模式必须同时满足：当前节点为 `.singleQuesId`，其原生 `data` 等于解析后的数字题目 ID，根节点 id 为 `question{ID}`，textarea 的 id/name 为 `answer{ID}`，实例 key 与字段 id 相等。原生根节点、字段 ID 和字段名称均需唯一，字段必须属于当前题目及 form1。

两种模式均核对唯一的既有实例、就绪状态、可编辑状态、iframe/container/document/body 关联及原生 setContent/getContent/sync 方法；editor.form 必须与 textarea.form 相同，editor.textarea 属性存在时必须对应该字段。保留实例及文档跨题共享检查，不创建或初始化编辑器，不按实例编号推测对应关系。

绑定记录命名模式和已验证的原生 ID，并纳入 `sameQuestionUEditor()` 比较。题目快照和动作执行前的重新读取继续检查实例、方法、节点、字段及表单是否变化。

## 可写资格与执行

合法绑定仍沿原有路径传递：rawQuestion → finishQuestion 的 UEditor writer 与能力 → 题目图可写 textarea → confirmed 作答关系 → 请求单元的预填资格 → questionPrefillCandidates → renderRunState。运行中、分析未完整结束、没有有效答案或存在独立策略限制时，按钮继续受原条件控制。

写入与回读代码未修改：通过文本节点转义答案、保留换行，再调用 `setContent()` 和 `sync()`；读取 `getContent()`、iframe body 与 textarea，三方归一化文本与目标一致才记录成功。保留已有不同答案、非文本内容、同步不一致及人工介入保护。不直接修改隐藏字段，不调用保存、暂存或提交接口。
